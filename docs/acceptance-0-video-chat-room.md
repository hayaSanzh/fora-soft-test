## 2. Принятые решения

### 2.1 Q1–Q4 — блокирующие, закрыты до первого коммита (задача 0.1)

| # | Решение | Обоснование и следствия |
|---|---|---|
| **Q1** Существующий репозиторий/скаффолд | **Нет, greenfield подтверждён фактом.** До группы 0 репозиторий содержал ровно 3 файла: PRD, TDD, Implementation Plan | Проверено: 0 файлов кода, нет `package.json`, `node_modules`, конфигов сборки/линтеров, Dockerfile, CI, каталогов `client`/`server`/`shared`; git-репозиторий не инициализирован. Сверять §3–§6 с существующими именами модулей не с чем — структура TDD §2.2 является и целевой, и фактической. Легаси-ограничений нет ни на одном слое |
| **Q2** TypeScript или plain JS | **TypeScript, `strict: true`** (компиляция в ES2022) | PRD §7 требует «JavaScript (ES6+)» — TS является его надмножеством, требование выполняется. Решающий довод: `shared/events.ts` как единый источник истины по контракту (§6.2) и zod-схемы, дающие валидацию и типы из одного описания (§10.3) — без типов оба механизма теряют половину смысла. Плюс DoD плана уже требует `tsc --noEmit`. Риск отклонения: если заказчик потребует именно plain JS, конструкции дизайна не меняются — типы уезжают в JSDoc (TDD §2.3) |
| **Q3** Среда деплоя и TLS | **Один Docker-контейнер (Node раздаёт статику + socket.io) за nginx; TLS терминирует nginx** | K8s/PaaS исключены осознанно: состояние в RAM делает сервер stateful и одноинстансным (§9.4, риск R3), оркестратор добавил бы только риск рестартов, каждый из которых рвёт все звонки. Целевые среды: `docker compose up` на хосте оценки, при появлении домена — тот же образ на VPS. **Открытая операционная позиция:** конкретный домен и способ выпуска сертификата (Let's Encrypt против корпоративного CA) не определены — это не блокирует ничего до задачи 15.3, LAN-проверки до тех пор идут по `mkcert` (§12.1). Требует подтверждения DevOps перед группой 15 |
| **Q4** Версия Node.js LTS | **Node 20 LTS** | Зафиксировано в `.nvmrc`; на среде разработки проверено фактически: `v20.19.6`. В `engines` попадёт вместе с `package.json` (задача 1.1). Node 20 покрывает всё, что нужно проекту: нативный `fetch`, стабильный ESM, поддержка socket.io 4 и Vite 5 |

### 2.2 Q5–Q11 — не блокирующие, зафиксированы дефолтами (задача 0.2)

| # | Вопрос | Дефолт | Переменная окружения |
|---|---|---|---|
| Q5 | потолок битрейта | **выключен** (`null`) | `VITE_MAX_VIDEO_BITRATE` |
| Q6 | набор символов имени | whitelist `\p{L}\p{N}` + пробел, `.`, `_`, `-`; ≤ **30** | `MAX_NAME_LEN` (схема — задача 2.3) |
| Q7 | длина сообщения / антифлуд | **500** символов; burst **5** + refill **1/с**, ответ `RATE_LIMITED` без разрыва сокета | `MAX_MESSAGE_LEN`, `CHAT_RATE_BURST`, `CHAT_RATE_REFILL` |
| Q8 | глубина истории чата | **200** сообщений (ring buffer) | `MAX_MESSAGES` |
| Q9 | индикация состояния соединения на плитке | **включена** | `VITE_SHOW_CONNECTION_STATE` |
| Q10 | системное сообщение при graceful shutdown | **да**, пауза **2 с** на доставку | `SHUTDOWN_NOTICE`, `SHUTDOWN_GRACE_MS` |
| Q11 | доступность `/health` | **только внутри сети** (loopback + приватные диапазоны; дублируется в nginx) | `HEALTH_INTERNAL_ONLY`, `HEALTH_ALLOWLIST` |

Ключевое свойство: **каждое из этих значений — конфигурация, а не код.** Уточнение любого из Q5–Q11 по ходу реализации не потребует правки логики; для Q5 и R1 (подстановка TURN) это проверено тестом.
