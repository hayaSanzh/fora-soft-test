## 2. Решения при реализации

**README написан для того, кто открывает проект впервые.** Поэтому в нём есть два раздела, которых нет в TDD:

- **таблица «адрес → работает ли камера»** — `http://localhost` работает, `http://192.168.1.10` нет, `https://192.168.1.10` работает. Это самая частая ошибка при первом LAN-прогоне, и объяснение («не secure context, браузер даже не покажет `navigator.mediaDevices`») стоит выше любых деталей архитектуры;
- **«Решения, которые видно только в коде»** — одиннадцать решений формата «почему так, а не иначе». Без этого раздела код выглядит либо очевидным, либо странным: например, почему камера выключается через `track.stop()`, а микрофон через `enabled = false` (у камеры обязан гаснуть аппаратный индикатор, а остановленную аудиодорожку пришлось бы получать заново и ренегоциировать).

**Ограничения описаны следствием для пользователя, а не формулировкой риска.** «Нет TURN» не сообщает ничего; «пара за симметричным NAT увидит „Нет соединения с участником“, остальная комната продолжит работать» — сообщает, что именно сломается и что останется живым.

**TDD обновлён на месте, а не скопирован в v2.** ★ Это отклонение от формулировки задачи 16.3, и оно осознанное: документ правился в каждой группе (v1.1 … v1.18), каждое расхождение реализации с дизайном фиксировалось сразу. Копия на 1300 строк начала бы расходиться с оригиналом при первой же правке — два источника истины про архитектуру хуже одного с историей версий.

**Счёт задач в плане исправлен.** Значилось «16 групп / 78 подзадач», фактически — 17 групп и 99 подзадач: группа 0 в счёт не входила, а внутри групп появились подзадачи, каждая по зафиксированной причине. Расхождение в шапке плана — мелочь, но именно такие мелочи заставляют сомневаться в остальных числах документа.

### 3.2а Трассировка требований — сплошная проверка

Утверждение «40 из 40» проверено не по галочкам в плане, а сопоставлением PRD с кодом и тестами. Проверка воспроизводима:

```bash
python3 - <<'EOF'
import re, pathlib
files = [f for pat in ('client/src/**/*.ts','client/src/**/*.tsx','server/src/**/*.ts',
                       'shared/src/**/*.ts','e2e/*.ts') for f in pathlib.Path('.').glob(pat)]
tests = "\n".join(f.read_text() for f in files if '.test' in f.name or '.spec' in f.name)
def hits(n, tag):
    d = len(re.findall(rf'{tag}-{n}\b', tests))
    r = sum(1 for a, b in re.findall(rf'{tag}-(\d+)\s*[…\.]{{1,3}}\s*(\d+)', tests) if int(a) <= n <= int(b))
    return d + r
for tag, total in (('ФТ', 40), ('US', 13)):
    print(tag, [n for n in range(1, total + 1) if hits(n, tag) == 0] or 'все покрыты')
EOF
```

★ **Находка аудита: ФТ-32 не был упомянут ни в одной строке кода или тестов.** Требование гласит «у создателя комнаты нет никаких особых прав; все участники равны» — то есть это **требование-отрицание**, выполненное отсутствием кода. Такие требования легко считать выполненными «по умолчанию»: понятия «владелец» в проекте действительно нет. Но именно поэтому они и уязвимы — привилегию первого участника ничто не мешает добавить позже, и ни один тест не упадёт.

Добавлены 3 теста (`presence.test.ts`): в модели участника нет полей роли (`Object.keys` строго `id`, `joinedAt`, `media`, `name`); снимок комнаты описывает всех участников одинаковым набором полей; выход создателя не закрывает комнату и не меняет прав остальных — второй участник продолжает отправлять сообщения, а третий входит нормально.

Дополнительно размечены US-7 (управление устройствами) и US-11 (обрыв у одного не ломает звонок): они были покрыты тестами, но ссылались только на соответствующие ФТ, из-за чего в трассировке выглядели пробелом.
