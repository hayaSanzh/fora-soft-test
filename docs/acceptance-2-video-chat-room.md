## 2. Решения при реализации

| Решение | Почему |
|---|---|
| Пакет разложен на 5 модулей (`protocol`, `limits`, `types`, `events`, `validation`) вместо одного `events.ts` из TDD §2.2 | Данные, транспорт и валидация меняются по разным причинам; barrel `index.ts` сохраняет единую точку импорта, поэтому для потребителей ничего не меняется |
| SDP и ICE описаны **структурно**, без `lib.dom` | Серверу DOM недоступен (`types: []`), а браузерные `RTCSessionDescriptionInit` / `RTCIceCandidateInit` присваиваются структурным типам без приведения — проверено пробником |
| Схемы — **фабрики от лимита** (`makeNameSchema(maxLen)`), а не константы с зашитым 30 | Иначе `MAX_NAME_LEN` из env менял бы конфигурацию, но не валидацию, и лимит расходился бы между UI и сервером |
| Лимиты живут в `shared/limits.ts` и служат дефолтами обеих конфигураций | Один литерал вместо трёх копий (схема, сервер, клиент) |
| `validate()` возвращает **код** ошибки (`INVALID_NAME`, `EMPTY_TEXT`, …), а не текст zod | Код уходит в ack (TDD §6.2), а русский текст берётся из `strings.ts` (задача 5.2). Смешивать нельзя: ack — часть контракта |
| Регулярные выражения для невидимых символов собраны из строк с escape-последовательностями | Литерал вида `/[<U+200B>]/` содержал бы невидимые символы в исходнике — такой код нельзя ни прочитать, ни отревьюить |
| Имя обязано начинаться с буквы или цифры | Иначе whitelist пропускает `---`, `. `, `_x`: формально допустимо, но именем не является |
| `"sideEffects": false` у пакета | Без этого barrel затягивал `zod` в клиентский бандл: 47.27 → 64.15 КБ gzip при том, что клиент валидацию ещё не использует. С флагом — снова 47.27 КБ |
| `mediaStateSchema` добавлена сверх трёх схем из 2.3 | `MediaState` приходит и в `room:join`, и в `media:state`; без общей схемы группа 4 написала бы свою |
| Полные payload-схемы (`joinPayloadSchema` и т. п.) **не** делались | Это сборка из готовых схем в серверных обработчиках — задачи 4.1 и 4.6 |

### 3.4 Живой пробник (временный, в репозиторий не попал)

Типизированный `Server<ClientToServerEvents, ServerToClientEvents, InterServerEvents, SocketData>` + два клиента `socket.io-client`; обработчики валидируют payload схемами из `shared`. **13 из 13 проверок пройдены:**

1. `room:join` → `ok: true`;
2. имя `'  Анна-Мария<ZWSP>  '` вернулось из ack как `'Анна-Мария'` — санитизация работает на транспорте, а не только в тесте;
3. `media` доехало без искажений;
4. снапшот содержит участника и историю;
5. системное сообщение о входе лежит в той же истории;
6. имя `<script>alert(1)</script>` → `INVALID_NAME`;
7. `roomId` `../../etc/passwd` → `INVALID_ROOM_ID`;
8. `peer:joined` доставлен первому участнику при входе второго;
9. `chat:message` → ack `{ok: true, id}`;
10. **текст `<img src=x onerror=alert(1)>` доставлен получателю как есть** — экранирование не на транспорте, а на выходе (TDD §10.3);
11. автор сообщения — очищенное имя;
12. `'   '` → `EMPTY_TEXT`;
13. 501 символ → `TEXT_TOO_LONG`.

Отдельно проверено, что контракт **ловит ошибки**. Негативный пробник дал три ожидаемые ошибки компиляции: опечатка в имени события (`room:jion`), пропущенное поле `media` в payload, несуществующий код ошибки (`ROOM_IS_FULL` → подсказка `ROOM_FULL`).

Честная деталь: при типизации положительного пробника `tsc` нашёл **две ошибки в самом пробнике** — обращение к `item.text` и `item.authorName` без предварительного сужения `ChatItem`. Это не дефект контракта, а ровно то поведение, ради которого union и выбран: без проверки `type === 'user'` доступ к полям пользовательского сообщения невозможен. Runtime-проверки при этом прошли все.

## 4. Найдено и исправлено

1. **Дефект санитизации имени в TDD §10.3.** Управляющие символы удалялись **до** сворачивания пробелов, поэтому `«Аня\nПетрова»` превращалось в `«АняПетрова»` — слова склеивались. Тест это поймал; в реализации `\t`, `\n`, `\r` не удаляются, а попадают под `\s+ → ' '`, zero-width удаляются полностью. TDD §10.3 дополнен примечанием.
2. **`zod` затягивался в клиентский бандл** (+17 КБ gzip) через barrel-реэкспорт, хотя клиент валидацию ещё не использует. Исправлено флагом `"sideEffects": false`; проверено по содержимому бандла, а не только по размеру.
3. **Числовые лимиты дублировались** в трёх местах (схемы, серверная и клиентская конфигурации). Сведены в `shared/limits.ts`.
4. **Схемы с зашитым лимитом обесценивали `MAX_NAME_LEN` / `MAX_MESSAGE_LEN` из env** — стали фабриками от лимита.
