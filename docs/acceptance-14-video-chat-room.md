## 2. ★ Главное: дефект, ломавший Firefox полностью

**Симптом.** Через ~1 секунду после входа второго участника Firefox показывал «Нет связи с сервером». Один участник в комнате — всё работало.

**Разбор.** Сокет закрывал **сам сервер**. В логе — `WARN: превышен лимит сигналинга: сокет отключён`. Замер числа кадров в WebSocket:

| Браузер | ICE-кандидатов на одно соединение 1:1 | Итого сигнальных событий |
|---|---|---|
| Chromium | 8 | 10 |
| **Firefox** | **99** | **101** |

Лимит был 100 событий за 10 секунд. То есть **одного звонка вдвоём хватало на превышение**, и защита от абьюза отсекала нормального пользователя.

**Почему это не поймали раньше.** Порог 100 был назначен как «столько человек не наберёт» и проверен тестами, которые задают лимит явно (`signalMax: 5`) — то есть проверяли механизм, но не **калибровку**. Все E2E до группы 14 шли только в Chromium, где кандидатов в 12 раз меньше. Дефект был виден только на другом движке.

**Исправление.** Порог поднят до 1000 с расчётом от худшего случая: 4 участника → 3 соединения mesh × ~100 кандидатов ≈ 300 событий, плюс офферы и ренегоциации — трёхкратный запас. Добавлен тест, привязывающий порог к `maxParticipants`, чтобы при изменении лимита участников расчёт не разошёлся с реальностью.

**Урок для документа (TDD §10.4):** любой порог, откалиброванный на одном движке, — скрытая несовместимость. Меры против абьюза опаснее отсутствия мер, когда отсекают нормальных пользователей: со стороны это выглядит как сбой сети, а не как срабатывание защиты.

## 3. Две проверки переведены из ручных в автоматические

**14.5, утечки ресурсов (риск R7).** План предполагал чтение `chrome://webrtc-internals` глазами. У этой страницы нет программного API — но **сами объекты доступны**, если перехватить их до старта приложения: `RTCPeerConnection` и `getUserMedia` обёрнуты через `addInitScript`. Проверяется ровно то, что смотрели бы вручную:

- после «Выйти» — `connectionState === 'closed'` у всех соединений и `readyState === 'ended'` у всех локальных дорожек;
- уход собеседника закрывает соединение с ним, но **не** гасит свои устройства (участник остался в комнате);
- повторный вход не накапливает открытые соединения: всего их становится больше, открытых — по-прежнему одно на собеседника.

**14.6, Firefox.** Фейковые устройства включаются не флагами, а настройками профиля (`media.navigator.streams.fake`). Прогоняется основной сценарий, а не весь набор: цель — поймать различия движков, а не перепроверить логику приложения второй раз. Тесты помечены `@cross-browser` и идут в **обоих** движках: если сценарий падает только в Firefox — дело в движке, если в обоих — в приложении.

## 4. Найдено и исправлено

1. **★ Лимит сигналинга отключал Firefox** — см. §2.
2. **★ Флаг потолка битрейта не был проверен во включённом состоянии.** Задача 14.7 велит включить `VITE_MAX_VIDEO_BITRATE` при упирании в канал — то есть это единственная мера против риска R2. Проверялось только выключенное состояние (`setParameters` не вызывается), а работает ли флаг — никто не проверял. Потолок вынесен в опции `PeerManager` (раньше читался из синглтона `config`, и включённое состояние было непроверяемым), добавлено 4 теста: `maxBitrate` попадает в каждый encoding видеоотправителя, не касается аудио, применяется при возврате камеры через `replaceTrack` и не применяется при её выключении.
3. **`grantPermissions` не поддерживается в Firefox.** В хелперах вызов пропускается по типу браузера, а не заворачивается в `try/catch`: молчаливое проглатывание ошибки скрыло бы и настоящие сбои выдачи разрешений.

## 5. Что осталось ручным и почему

| Проверка | Почему автоматика не может |
|---|---|
| Аппаратный индикатор камеры (14.2) | состояние светодиода недоступно из браузера ни одним API |
| Задержка ≤ 500 мс в LAN (14.3) | на loopback нет ни сети, ни разных машин. **Измеримость** проверена автоматически: поля `currentRoundTripTime` и `jitterBufferDelay` заполняются |
| Отключение USB-камеры (14.4) | драйверное событие `track.onended` программно не воспроизвести; логика обработки покрыта unit-тестами |
| Отсутствие эха (14.6) | субъективная оценка на слух |
| Edge (14.6) | Playwright не поддерживает Edge с фейковыми устройствами |
| CPU при 4 участниках (14.7) | зависит от машины; Playwright не измеряет CPU достоверно. **Механизм** ограничения битрейта проверен автотестом |

## 6. Что нужно проверить руками

Полный чек-лист — `docs/manual-verification-video-chat-room.md`. Здесь — что важнее всего именно после этой группы:

```bash
npm run verify        # 623 теста
npm run test:e2e      # 40 E2E: Chromium + Firefox
npm run serve         # http://localhost:3001
```

1. **★★ Firefox работает** (исправление §2). Откройте комнату в Firefox, второй вкладкой — тоже Firefox. Ожидается: видео и звук в обе стороны, **соединение держится дольше минуты**. Раньше через секунду появлялось «Нет связи с сервером».
2. **★ Firefox ↔ Chrome.** Один участник в Firefox, второй в Chrome: звонок, чат, тумблер камеры.
3. **★ Индикатор камеры (14.2).** Выключить камеру → **светодиод на корпусе гаснет**. Это проверка того, что дорожка остановлена, а не заглушена: иначе пользователь думает, что его не видно, а его видно.
4. **Отключение USB-камеры (14.4).** Выдернуть камеру во время звонка → тумблер переходит в «Включить камеру», у собеседника заглушка, баннер «Устройство отключено», **звонок и чат продолжают работать**.
5. **Эхо (14.6).** 4 участника в одном помещении без наушников → эхо есть (это физика). Главное: **никто не слышит собственный голос**.
6. **CPU и битрейт (14.7).** 4 участника → записать CPU. При проблемах с каналом: `VITE_MAX_VIDEO_BITRATE=800000 npm run build && npm start` → проверить `outbound-rtp → targetBitrate` в `chrome://webrtc-internals`.
7. **LAN по HTTPS (14.3).** Между физическими машинами через `mkcert` на LAN-IP → замерить RTT, ожидается ≤ 500 мс.

## 7. Готовность к группе 15

- E2E разделены на три project'а, что задаёт форму CI-шага: `npm run test:e2e` покрывает Chromium и Firefox одной командой;
- порог сигналинга стал конфигурируемым и обоснованным — в деплой-документацию (15.2, nginx) уйдёт замечание, что реверс-прокси не должен урезать WebSocket-таймауты, иначе воспроизведётся тот же симптом «Нет связи с сервером» по другой причине;
- чек-лист ручных проверок готов и может войти в README (16.1) как раздел «что проверить перед сдачей».

**Вывод: выполнено всё, что не требует железа. Ключевая ценность группы — кросс-браузерный прогон, который нашёл дефект, делавший приложение неработоспособным для всех пользователей Firefox. Пункты 14.2, 14.3, 14.4, 14.7 и Edge ждут прогона на устройствах — без них утверждение «работает на 4 участниках» не подкреплено замерами.**
