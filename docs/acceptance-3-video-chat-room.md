## 2. Решения при реализации

| Решение | Почему |
|---|---|
| Лимиты, `now()` и `generateId()` инжектируются через конструктор | Иначе тесты ring buffer и истории пришлось бы писать на реальных `Date.now()` и `nanoid`: получились бы либо недетерминированные утверждения, либо «тест на моках» вместо теста поведения |
| Повторный `join` тем же `socket.id` → `ALREADY_JOINED` | Тихая перезапись участника скрыла бы ошибку клиента и позволила бы одному сокету занять слот дважды. Код уже есть в контракте §6.2. ФТ-29 не нарушено: у каждой вкладки свой сокет |
| `snapshot()` возвращает **копии** массивов | Иначе вызывающий код может изменить состояние комнаты в обход стора — проверено тестом |
| `addMessage(roomId, draft)` принимает заготовку без `id`/`ts` | Время обязано быть серверным (ФТ-22 говорит про локальное время **отображения**), `id` нужен как React-key и для идемпотентности. Тип заготовки не позволяет передать их снаружи |
| Обрезка истории через `splice(0, length - max)`, а не `shift()` | Одна операция вместо N, а также корректная обрезка, если лимит уменьшили на живой комнате |
| `updateMedia` и `getParticipant` добавлены сверх 3.1–3.4 | Владелец состояния — только стор; иначе задачи 4.4 (проверка адресата сигналинга) и 4.5 (`media:state` в снапшоте) начали бы менять `Map` напрямую |
| `stats()` в сторе, а не в HTTP-слое | `/health` не должен знать внутреннее устройство комнат; шов `getStats()` из задачи 1.3 для этого и был сделан |
| Ветка `if (size === 0) rooms.delete()` внутри `join` сохранена из TDD | При штатном `maxParticipants ≥ 1` недостижима, но защищает от конфигурации `MAX_PARTICIPANTS=0`: иначе каждый отказ оставлял бы в памяти пустую комнату. Покрыта тестом |

### 3.4 Проверка теста-стража мутацией

Требование ФТ-7 держится не на комментарии, а на двух тестах. Чтобы убедиться, что они действительно защищают инвариант, `join()` был **временно** сделан асинхронным с `await Promise.resolve()` между проверкой лимита и вставкой:

- ✅ тест-страж (чтение исходника + проверка, что метод не `AsyncFunction`) — **упал**;
- ✅ тест «10 синхронных `join` впускают ровно 4» — **упал**;
- ✅ упали ещё 9 тестов, зависящих от синхронного результата.

Исходник восстановлен, 28/28 снова зелёные. То есть регрессия атомарности не может пройти в main незамеченной.

## 4. Известные ограничения

| Позиция | Статус |
|---|---|
| `/health` показывает `rooms: 0` на живом сервере | ожидаемо: обработчики `room:join` появятся в задаче 4.1, до этого некому наполнять стор. Интеграция стора и `/health` проверена тестом |

| `SystemMessageKind: 'shutdown'` пока не используется | задача 4.9 (graceful shutdown, Q10) |
| Тест-страж читает исходник `RoomStore.ts` | нестандартный приём, но требование F-05 формулируется именно как «в этой функции нет `await`» — иначе его нечем проверить, кроме код-ревью |

- API стора покрывает все потребности обработчиков: `join` / `leave` (4.1, 4.3), `getParticipant` для проверки адресата сигналинга (4.4), `updateMedia` (4.5), `addUserMessage` для чата (4.6), `snapshot` для ack (4.1), `addSystemMessage` для входа/выхода (4.3);
