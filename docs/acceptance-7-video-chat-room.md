## 2. Решения при реализации

| Решение | Почему |
|---|---|
| Модуль **не знает** ни про React, ни про `PeerManager`: дорожки уходят колбэками `onAudioTrack` / `onVideoTrack` | `replaceTrack` вызывает группа 8. Благодаря этому все ветки проверяются без браузера, а сам `replaceTrack` в бандле группы 7 отсутствует по построению — что и подтверждено проверкой бандла |
| Состояние = «пользователь хочет» **И** «дорожка жива» | Отдельный флаг тумблера нужен, чтобы после потери устройства (ФТ-20) состояние честно стало `false`, а повторное включение прошло через новый `getUserMedia` |
| Включение тумблера при отсутствующей дорожке **пробует `getUserMedia` заново** | Пользователь мог разрешить доступ в настройках браузера или подключить устройство. Требовать перезахода в комнату из-за этого — плохой UX и лишний слот на сервере |
| Выключение камеры: сначала `onVideoTrack(null)`, потом `track.stop()` | Сначала перестаём отправлять, потом освобождаем железо. Обратный порядок даёт кадр «чёрного экрана» у собеседников до того, как они узнают о выключении |
| Микрофон **никогда** не останавливается тумблером | `enabled = false` мгновенно и не требует ренегоциации; `stop()` заставил бы платить `getUserMedia` + SDP-обмен за каждое включение (ФТ-15) |
| `OverconstrainedError` → повторный запрос без ограничений | На дешёвых веб-камерах 720p недостижимо; отказывать в видео из-за разрешения неправильно (TDD §4.4) |
| Дорожка, полученная **после** `teardown()`, немедленно останавливается | Гонка: пользователь ушёл, пока браузер показывал диалог разрешений. Иначе камера остаётся включённой, а интерфейса, который её показывает, уже нет (риск R7) |
| `ondevicechange` только уведомляет UI | Исчезновение живой дорожки приходит событием `ended` и обрабатывается там; дублировать логику не нужно |
| Self-view `<video>` смонтирован **всегда**, даже при выключенной камере | Условный рендеринг `<video>` — самая частая регрессия в таких проектах: он убивает и аудио пира (риск R5). Правило соблюдается с первого же появления элемента |
| `srcObject` присваивается напрямую через `ref` | Дорожки не должны проходить через состояние React — иначе видео мигает на каждое изменение (TDD §4.6, §9.3) |

## 4. Найдено и исправлено

### 4.1 Дефекты, найденные ручной приёмкой

**1. Self-view оставался чёрным до первого переключения камеры (индикатор при этом горел).**

Причина: `onVideoTrack` срабатывает во время `acquire()`, то есть на экране `acquiringMedia`, где `<video>` ещё не отрендерен. `selfVideoRef.current` был `null`, `srcObject` не присваивался, а при последующем монтировании элемента никто присвоение не повторял. Переключение камеры «лечило» симптом, потому что вызывало `onVideoTrack` заново — уже при смонтированном элементе.

Иронично, что это ровно та ошибка, от которой предостерегает риск R5: **условно смонтированный `<video>`**. Для self-view последствие мягкое (чёрный экран), для плитки пира то же самое убило бы аудио.

*Исправление:* `srcObject` присваивается в двух местах — при появлении дорожки **и** в момент монтирования элемента (через callback-ref `attachSelfVideo`). В группе 10 элемент станет постоянно смонтированным `VideoTile`, но правило «присваивать и на mount» останется.

**2. Пометки «Микрофон выключен» / «Видео выключено» не появлялись у других участников.**

Здесь дефекта в логике не оказалось: пробник с **настоящими** модулями (`LocalMedia` + `startRoomConnection` + `roomReducer`) против настоящего сервера показал, что состояние доезжает корректно во всех направлениях, включая снапшот позднего участника. Причина была процедурной: **пометки были добавлены после последней сборки**, а `npm run verify` бандл не собирал — в браузере открывался устаревший `client/dist`.

*Исправление сразу на трёх уровнях, чтобы этот класс путаницы не повторился:*

- `npm run verify` теперь **включает `npm run build`** — после проверки в `client/dist` всегда свежий код;
- добавлен скрипт `npm run serve` (сборка + запуск) для ручных проверок одной командой;
- сервер при старте **логирует время сборки клиента** (`builtAt`) или предупреждает, что клиент не собран, — устаревший бандл теперь видно сразу в логе.

Дополнительно логика подписи участника вынесена в чистую функцию `describeParticipant()` и покрыта 5 тестами: пометки для микрофона, камеры, обоих устройств, «(вы)» и отсутствие внутреннего id в подписи (ФТ-30).

### 4.2 Найдено при разработке

1. **Мой тест на гонку «ушёл во время запроса разрешения» висел 15 секунд и падал.** Я вызывал `teardown()` до того, как запрос камеры реально уходил в фейковые устройства, поэтому промис никогда не разрешался. Исправлено ожиданием факта запроса; тест теперь выполняется за 68 мс и проверяет именно то, что должен.
2. **TypeScript сузил тип до `never`** в замыкании промиса (`let resolveVideo` присваивается внутри executor'а) — переписано через объект-holder.

## 6. Что нужно проверить руками (нужно железо)

Автоматика проверила логику на фейковых устройствах. **Три вещи проверяются только на реальном железе** — это те самые пункты, которые план относит к задачам 14.2 и 14.4.

```bash
npm run serve            # сборка + запуск одной командой
# откройте http://localhost:3001 (обязательно localhost — на LAN-IP без HTTPS камера недоступна)
```

В логе запуска сервера есть строка `клиент найден` с полем `builtAt` — убедитесь, что время сборки свежее. Если там `клиент не собран`, значит бандла нет.

1. **Запрос доступа и self-view (ФТ-13; исправлено, §4.1 п.1).** Имя → «Создать комнату» → браузер спрашивает доступ → разрешите. Ожидаемо: **видео появляется сразу**, без необходимости переключать камеру. Кнопки — «Выключить микрофон» и «Выключить камеру».
2. **★ Аппаратный индикатор камеры (ФТ-19) — главная проверка группы.** Нажмите «Выключить камеру». Ожидаемо: **светодиод камеры физически гаснет** (на ноутбуке — лампочка рядом с объективом), self-view становится чёрным, появляется надпись «Видео выключено», кнопка меняется на «Включить камеру». Нажмите её — индикатор загорается снова, видео возвращается (задержка 150–600 мс нормальна).
3. **Микрофон остаётся живым (ФТ-15).** Нажмите «Выключить микрофон». Ожидаемо: индикатор микрофона в браузере (значок в адресной строке / вкладке) **не исчезает** — дорожка жива и отдаёт тишину. Это правильно: так включение мгновенно.
4. **Состояние видно другим (ФТ-16, ФТ-18; исправлено, §4.1 п.2).** Откройте комнату во второй вкладке. Выключите микрофон в первой → **во второй вкладке рядом с вашим именем появилось «· Микрофон выключен»**. Выключите камеру → добавилось «· Видео выключено». Включите обратно — пометки исчезли. Проверьте и в обратную сторону: выключите устройства во второй вкладке, посмотрите на первую.
5. **★ Отказ в доступе не выкидывает из комнаты (ФТ-33, US-12).** В настройках сайта (значок замка/камеры в адресной строке) запретите камеру и микрофон, перезагрузите страницу и войдите заново. Ожидаемо: **вы всё равно в комнате**, оба тумблера в положении «Включить», под ними красная строка «Нет доступа к камере или микрофону…». Экрана ошибки быть не должно.
6. **★ Потеря устройства (ФТ-20).** Если есть USB-камера: войдите в комнату с включённой камерой и **физически отсоедините её**. Ожидаемо: тумблер сам ушёл в «Включить камеру», появилась строка «Устройство отключено», во второй вкладке — «Видео выключено». Подключите камеру обратно и нажмите «Включить камеру» — видео вернулось. (На ноутбуке со встроенной камерой этот пункт воспроизвести нельзя.)
7. **★ Камера гаснет после выхода (ФТ-27, риск R7).** Включите камеру и нажмите «Выйти». Ожидаемо: **светодиод камеры гаснет сразу**, а не через несколько секунд. То же при закрытии вкладки. Дополнительно можно посмотреть `chrome://webrtc-internals` — активных дорожек остаться не должно (формально это задача 14.5).
8. **Отказ во время диалога.** Войдите и, пока браузер показывает диалог разрешений, нажмите «Выйти» (или закройте вкладку). Ожидаемо: индикатор камеры не загорается вообще.

Если п. 2 или п. 7 не выполняются — это дефект: `stop()` либо не вызывается, либо вызывается не для всех дорожек.

## 7. Готовность к группе 8

- `LocalMedia` отдаёт дорожки колбэками — `PeerManager` подпишется на них и вызовет `replaceTrack` на всех соединениях;
- `getAudioTrack()` / `getVideoTrack()` позволяют подставить дорожки в только что созданное соединение (нужно для 8.2: два фиксированных трансивера + `replaceTrack`);
- `teardownMedia` уже вызывается на всех терминальных путях соединения — группе 9 останется добавить туда закрытие peer-соединений;
- `config.maxVideoBitrate` (Q5) готов к применению в `sender.setParameters()`.

**Вывод: группа 7 принята автоматикой; ручные проверки §6 (особенно п. 2 и 7) подтверждают ФТ-19 и ФТ-27, которые невозможно проверить без железа.**
