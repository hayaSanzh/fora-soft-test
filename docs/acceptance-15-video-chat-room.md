## 2. ★ Главное: прод-образ не запускался

**Симптом.** `docker run video-chat-room:local` → контейнер немедленно завершается:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'nanoid'
    imported from /app/server/dist/RoomStore.js
```

**Причина.** npm не обязан поднимать все зависимости в корневой `node_modules`. В этом проекте `nanoid` он размещает **вложенно** — в `server/node_modules` и `client/node_modules` (по 68 КБ), — а `Dockerfile` копировал в рантайм только корневой каталог:

```dockerfile
COPY --from=prod-deps /app/node_modules ./node_modules   # server/node_modules остался за бортом
```

**Почему дефект прожил с группы 1 до группы 15.** `docker build` завершается успешно и в исправном, и в сломанном случае: сборка не запускает приложение. А образ никто не запускал — в группе 1 его собрали, и на этом остановились. Ни один из 663 автотестов не проверял артефакт доставки, потому что все они работают с исходниками или с `npm start` на хосте.

**Исправление в два слоя.**

1. Копирование вложенных зависимостей воркспейса. В стадии `prod-deps` добавлен `mkdir -p server/node_modules`, чтобы `COPY` не зависел от того, вложил npm зависимость или поднял: иначе сборка ломается при обновлении npm, а не при ошибке в коде.
2. **Проверка разрешимости импортов внутри образа.** Каждый собранный модуль импортируется в отдельном процессе; точка входа исключена намеренно — её импорт поднял бы сервер и подвесил сборку. Теперь ошибка такого класса ломает `docker build`, а не прод.

```dockerfile
RUN set -e; \
    for module in $(find server/dist shared/dist -name '*.js' ! -name 'index.js'); do \
      node --input-type=module -e "await import('/app/$module')"; \
    done
```

**Вывод, который важнее самого дефекта:** «собралось» не означает «работает». Поэтому шаг 6 пайплайна не ограничивается `docker build` — отдельный шаг **запускает образ** и дёргает `/health`, страницу и SPA-fallback.

## 3. Решения при реализации

**CI: четыре job'а вместо линейного списка.** `verify` → `e2e` → `image` → `deploy`. Дорогие проверки не запускаются, пока не прошли дешёвые: если упал `tsc`, нет смысла ставить браузеры и собирать образ. К шагу 2 добавлен `format:check` — расхождение формата накапливалось три группы именно потому, что проверка не входила в единую команду.

**Job деплоя отключён `if: false`, а не удалён.** В нём описана вся процедура — проверка занятости комнат перед рестартом, сохранение предыдущего образа, деплой, проверка `/health`, автоматический rollback при неудаче — и перечислено, что нужно для включения (пять секретов и GitHub Environment с подтверждением). Молча непрогоняемый деплой хуже отсутствующего: он создаёт видимость CD.

**nginx: `Connection` через `map`, а не строкой.** Статичный `Connection: upgrade` ломает keep-alive для обычных HTTP-запросов к `/socket.io/`. Ещё три решения, каждое объяснено в самом файле: `proxy_read_timeout 300s` (дефолтные 60 с рвут сигнальный сокет в тихом звонке, а auto-reconnect выключен по ФТ-31), `proxy_buffering off`, ограничение `/health` по адресу **дополнительно** к ограничению в приложении — один слой защиты равен нулю слоёв, если в `TRUST_PROXY` ошибка.

**Статика в nginx не дублируется.** Её раздаёт Node (один origin, §12.2). Второй путь к сборке разошёлся бы с тем, что проверено тестами.

**Проверка сети — инструмент, а не абзац в документации.** `scripts/check-network.mjs` отправляет настоящий STUN Binding Request (RFC 5389, без зависимостей), разбирает `XOR-MAPPED-ADDRESS` и печатает внешний адрес. Причина: закрытый UDP выглядит для пользователя **как дефект приложения** — плашка «Нет соединения с участником» при работающем чате, — и проверку нужно уметь выполнить за десять секунд до начала разбора.

## 6. Что нужно проверить руками

```bash
# 1. Проверка сетевых предусловий — работает в любой среде
node scripts/check-network.mjs

# 2. Синтаксис nginx без установки nginx
docker run --rm -v "$PWD/deploy/nginx:/etc/nginx/conf.d:ro" nginx:alpine nginx -t
# «cannot load certificate» ожидаемо: синтаксис уже разобран

# 3. Прод-образ собирается и ЗАПУСКАЕТСЯ
docker build -t video-chat-room:local .
docker run -d --name vc-check -p 127.0.0.1:3201:3001 video-chat-room:local
sleep 3 && curl -s http://127.0.0.1:3201/health   # ждём {"status":"ok",...}
docker rm -f vc-check
```

4. **★ Убедиться, что дефект был настоящим.** Уберите из `Dockerfile` строку с `server/node_modules` и проверьте, что сборка теперь **падает** на проверке импортов (раньше она проходила, а падал контейнер):

```bash
cp Dockerfile /tmp/Dockerfile.bak
grep -v "server/node_modules ./server/node_modules" /tmp/Dockerfile.bak > Dockerfile
docker build -t video-chat-room:broken .    # ждём ERR_MODULE_NOT_FOUND на шаге проверки импортов
cp /tmp/Dockerfile.bak Dockerfile
```

5. **Проброс WebSocket через nginx** — процедура в `docs/deploy-video-chat-room.md` §2: поднять оба слоя и пройти звонок в двух вкладках по `https://localhost`. Это единственная проверка, подтверждающая заголовки `Upgrade`.

6. **`docker compose up`** — прод-подобный прогон одним контейнером на `http://localhost:3001`.
