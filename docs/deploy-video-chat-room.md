# Процедура деплоя и rollback — «Видеочат-комната»

| | |
|---|---|
| **Документ** | Runbook деплоя (задачи IP 15.2, 15.3, 15.4) |
| **Основан на** | TDD §12.2–§12.5 |
| **Топология** | nginx (TLS + WebSocket upgrade) → Node (статика + socket.io), **один инстанс** |

---

## 0. Главное операционное следствие архитектуры

**Любой рестарт процесса уничтожает все активные комнаты и звонки.** Состояние живёт в RAM (TDD §12.4), auto-reconnect отключён по требованию ФТ-31, поэтому все участники окажутся на экране «Нет связи с сервером» и должны будут войти заново.

Из этого следует три правила, которые важнее любых деталей ниже:

1. **Один инстанс — требование архитектуры, а не упрощение.** Второй сервер в upstream разведёт участников одной комнаты по разным процессам, и они не увидят друг друга.
2. **Деплой — в окно низкой активности.** Перед рестартом смотреть `/health`: поле `participants` показывает, сколько звонков будет прервано.
3. **Blue-green не спасает.** Он даёт нулевой downtime для новых комнат, но существующие не переносит: состояние принципиально непереносимо.

## 1. Предусловия среды

### 1.1 Сеть (задача 15.4)

```bash
node scripts/check-network.mjs
```

Скрипт отправляет настоящий STUN Binding Request и печатает внешний адрес машины.

| Результат | Что значит |
|---|---|
| `✔ Исходящий UDP работает` | клиенты соберут srflx-кандидатов; звонки между разными сетями возможны без TURN |
| `✘ STUN недостижим` | **приложение не заработает между сетями.** Обхода без TURN нет (риск R1). Внутри одной подсети звонок состоится на host-кандидатах |

★ Чего проверка не подтверждает: прохождение произвольных высоких UDP-портов **между двумя клиентами**. Это проверяется только звонком между машинами в разных сетях.

Симптом закрытого UDP для пользователя — плашка «Нет соединения с участником» (ФТ-34) при работающем чате и списке участников. То есть выглядит как дефект приложения, поэтому проверку стоит выполнить **до** разбора.

### 1.2 TLS

HTTPS не «желателен», а обязателен: без secure context браузер не даёт `getUserMedia` вовсе (единственное исключение — `localhost`). На `http://<LAN-IP>` приложение честно покажет экран «страница открыта без HTTPS» (ФТ-36), но работать не будет.

## 2. nginx (задача 15.2)

Конфигурация: `deploy/nginx/video-chat.conf`. Перед установкой заменить `video-chat.example.com` на реальный домен и указать пути к сертификатам.

```bash
sudo cp deploy/nginx/video-chat.conf /etc/nginx/conf.d/
sudo nginx -t && sudo systemctl reload nginx
```

Проверка синтаксиса без установки nginx на машину:

```bash
docker run --rm -v "$PWD/deploy/nginx:/etc/nginx/conf.d:ro" nginx:alpine nginx -t
# «cannot load certificate» при этом ожидаемо: синтаксис уже разобран
```

### Что в этой конфигурации критично

| Директива | Что сломается без неё |
|---|---|
| `proxy_set_header Upgrade` + `Connection $connection_upgrade` | **WebSocket молча не поднимется**: socket.io получит 400 на handshake, пользователь увидит «Нет связи с сервером» — симптом не отличим от лежащего приложения |
| `proxy_read_timeout 300s` | дефолтные 60 с рвут сигнальный сокет в тихом звонке; участника выбросит на экран ошибки посреди разговора, и auto-reconnect его не вернёт (ФТ-31) |
| `proxy_buffering off` | кадры WebSocket будут копиться в буфере вместо немедленной доставки |
| `map $http_upgrade $connection_upgrade` | статичный `Connection: upgrade` ломает keep-alive для обычных HTTP-запросов к `/socket.io/` |
| `allow`/`deny` на `/health` | счётчики комнат станут доступны наружу. Приложение ограничивает доступ и само (Q11), но один слой защиты — это ноль слоёв, если в `TRUST_PROXY` ошибка |

### Проверка проброса WebSocket через прокси

`nginx -t` проверяет синтаксис, но **не** проброс. Полная проверка — поднять оба слоя и пройти звонок:

```bash
# сертификат на localhost
mkcert localhost   # или openssl req -x509 ... -subj "/CN=localhost"

# приложение
docker run -d --name vc-app --network host -e HOST=127.0.0.1 video-chat-room:local

# nginx с подменённым доменом и путями к сертификату
sed -e 's#video-chat.example.com#localhost#g' -e 's#/etc/letsencrypt/live/localhost/#/certs/#g' \
    deploy/nginx/video-chat.conf > /tmp/nginx-test/conf/test.conf
docker run -d --name vc-nginx --network host \
  -v /tmp/nginx-test/conf:/etc/nginx/conf.d:ro -v /tmp/certs:/certs:ro nginx:alpine

# проверки
curl -sk https://localhost/ -o /dev/null -w 'страница: %{http_code}\n'
curl -sk https://localhost/health
curl -sk -o /dev/null -w 'SPA-fallback: %{http_code}\n' https://localhost/RoomAAAAAAAA
```

Затем открыть `https://localhost` в двух вкладках и убедиться, что звонок поднимается: это и есть проверка `Upgrade`-заголовков. Если страница открывается, а участники не видят друг друга — дело в них.

Проверка рукопожатия одной командой:

```bash
curl -sk -i -N --http1.1 \
  -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" -H "Sec-WebSocket-Version: 13" \
  "https://<домен>/socket.io/?EIO=4&transport=websocket" | head -3
# ждём: HTTP/1.1 101 Switching Protocols
```

★ **`--http1.1` обязателен, и это не формальность.** Без флага curl договаривается на HTTP/2 (ALPN), а в HTTP/2 заголовка `Upgrade` не существует — придёт `400`, и конфигурация будет выглядеть сломанной, хотя она исправна. Браузеры для `wss://` всегда открывают отдельное соединение HTTP/1.1, поэтому проверять нужно так же. На этом легко потерять час, разбирая несуществующий дефект.

## 3. Деплой

```bash
# 1. Проверить, кого прервём
curl -fsS http://127.0.0.1:3001/health     # {"status":"ok","rooms":N,"participants":M}

# 2. Сохранить текущий образ для rollback
docker tag video-chat-room:current video-chat-room:previous

# 3. Забрать и переключить
docker pull "$REGISTRY/video-chat-room:$SHA"
docker tag "$REGISTRY/video-chat-room:$SHA" video-chat-room:current
docker compose up -d --no-deps app

# 4. Дождаться здоровья
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:3001/health | grep -q '"status":"ok"' && break
  sleep 2
done
```

Graceful shutdown при рестарте (Q10, §12.4): по `SIGTERM` сервер рассылает системное сообщение «Сервер завершает работу», ждёт 2 с на доставку, затем **принудительно** закрывает соединения. Полное время выхода ≈ 2,3 с.

★ Принудительное закрытие обязательно: `httpServer.close()` только перестаёт принимать новые соединения и **ждёт**, пока закроются существующие. Браузер держит keep-alive для статики десятками секунд — из-за этого процесс однажды висел 81 секунду (найдено на ручной приёмке группы 9).

## 4. Rollback

```bash
docker tag video-chat-room:previous video-chat-room:current
docker compose up -d --no-deps app
curl -fsS http://127.0.0.1:3001/health | grep '"status":"ok"'
```

Откат данных не требуется и невозможен: **БД нет, миграций нет, состояние в RAM**. Единственное следствие откатa — те же прерванные звонки, что и при деплое.

Если `/health` не отвечает после откатa — смотреть логи контейнера:

```bash
docker logs --tail 50 video-chat-room
```

Самая вероятная причина при первом деплое нового образа — незакрытая зависимость (`ERR_MODULE_NOT_FOUND`). Именно такой дефект был найден в группе 15: образ собирался успешно, но падал при старте, потому что npm разместил `nanoid` в `server/node_modules`, а Dockerfile копировал только корневой. Теперь это ловится **на этапе сборки** — в образе есть шаг проверки разрешимости импортов.

## 5. Флаги окружения

Полный перечень — TDD §12.5. Что чаще всего меняют в эксплуатации:

| Флаг | Дефолт | Когда менять |
|---|---|---|
| `SIGNAL_RATE_MAX` | `1000` | если в логах `превышен лимит сигналинга` при нормальной работе. Порог выведен из измерения: Firefox присылает ~99 ICE-кандидатов на соединение против 8 у Chromium (группа 14) |
| `VITE_MAX_VIDEO_BITRATE` | выключен | при упирании в канал на 4 участниках. Сборочный флаг: требует пересборки клиента |
| `PING_INTERVAL` / `PING_TIMEOUT` | `10000` / `5000` | скорость обнаружения обрыва; уменьшать осторожно — ложные разрывы на плохой сети |
| `SHUTDOWN_GRACE_MS` | `2000` | пауза перед закрытием соединений при рестарте |
| `HEALTH_INTERNAL_ONLY` | `true` | оставить `true`; при внешнем мониторинге добавить адрес в `HEALTH_ALLOWLIST`, а не открывать всем |
| `TRUST_PROXY` | `loopback` | должен соответствовать реальной цепочке прокси, иначе ограничение `/health` по адресу перестаёт работать |

## 6. Что проверить после деплоя

- [ ] `/health` отвечает `{"status":"ok"}` (изнутри сети).
- [ ] Страница открывается по `https://<домен>/`.
- [ ] Прямой переход по ссылке-приглашению `https://<домен>/<roomId>` отдаёт 200, а не 404 (SPA-fallback).
- [ ] Звонок между двумя браузерами: видео и звук в обе стороны — это и есть проверка `Upgrade`-заголовков nginx.
- [ ] `node scripts/check-network.mjs` на хосте сервера: исходящий UDP открыт.
- [ ] В логах нет `превышен лимит сигналинга` при обычном звонке.
- [ ] `docker logs` не содержит `ERR_MODULE_NOT_FOUND` и прочих ошибок старта.
